# FEASIBILITY — USB 通信の成立可能性の検証報告

対象: 実装順序の 1 番「実機 iPhone と Fedora 間の USB 通信を検証する」。

結論を先に書きます。

> **原理上は成立し得る。前例もある。ただし本プロジェクトのアプリ（TCP 18765）について、ユーザーの実機と iOS バージョンで届くかは未検証であり、実機での最終確認は未実施です。**
>
> この文書は「できるはず」の根拠と「まだ分からないこと」を分けて書いたものです。実機確認が終わるまで、USB 疎通を検証済みとして扱わないでください。

関連文書: [BRIDGE-PROTOCOL.md](BRIDGE-PROTOCOL.md)（§0 トランスポート、§5 未決定事項）、[REAL-DEVICE-TEST.md](REAL-DEVICE-TEST.md)（実機手順）、[../scripts/verify-usb-fedora.sh](../scripts/verify-usb-fedora.sh)（検証スクリプト）

---

## 1. 何を検証すべきか

成立が必要なのは次の連鎖です。どれか 1 つでも欠けると全体が成立しません。

```text
[Fedora] iphone-fido daemon
| 127.0.0.1:18766 へ TCP 接続
[Fedora] iproxy 18766 18765
| libusbmuxd 経由で usbmuxd に要求
[Fedora] usbmuxd
| USB (iPhone とのペアリング / trust が前提)
[iPhone] 端末内 usbmux 相当の機構が、アプリの待ち受けソケットへ中継
| TCP 18765
[iPhone] iphone-fido アプリ (NWListener, フォアグラウンド)
```

検証すべき問いは 3 つに分けられます。

| # | 問い | この文書での結論 |
|---|---|---|
| Q1 | usbmuxd / iproxy という仕組み自体は、PC から端末上の待ち受けポートへ届くのか | 原理・前例ともに Yes（§2） |
| Q2 | 非脱獄の通常アプリ（サイドロード含む）の待ち受けポートにも届くのか | 前例はあるが条件付き。iOS バージョン依存で要実機確認（§2、§3） |
| Q3 | ユーザーの Fedora + iPhone の組み合わせで、本アプリの 18765 へ実際に届いたか | **未実施・未検証**（§4） |

## 2. 原理上の可否と根拠

### 2.1 usbmuxd の仕組み

- iPhone は USB 接続時に、PC 側デーモン `usbmuxd` と通信するプロトコルを持っています。Linux では `usbmuxd` パッケージがその役割を担い、端末の列挙、ペアリング記録の管理、端末上のサービス／ソケットへの接続中継を提供します。
- `usbmuxd` は「端末上の待ち受けている localhost ソケットへ中継できる」設計です。PC 側のプログラムは usbmux プロトコルで「端末のポート N へ接続したい」と要求し、usbmuxd が USB 越しにその接続を運びます。
- `iproxy`（libusbmuxd-tools）はその薄い転送ツールです。`iproxy <PC側ポート> <端末側ポート>` で PC の localhost に待ち受けを作り、来た接続を usbmux 経由で端末側ポートへ流します。本プロジェクトでは BRIDGE-PROTOCOL §0 の通り `iproxy 18766 18765` を使います。
- 前提として、PC と iPhone の間にペアリング（trust）が確立し、ペアリング記録が PC 側に保存されている必要があります。未ペアリングだと usbmuxd 経由の接続は拒否されます。確立は `idevicepair pair` で行い、iPhone 側で「信頼する」の確認が要ります。

### 2.2 非脱獄アプリへの転送の前例

- WebDriverAgent（WDA）は非脱獄の実機上で動くアプリで、TCP ポート 8100 で HTTP サーバーを待ち受けます。PC 側の自動テスト基盤は日常的に `iproxy 8100 8100` 相当の転送で WDA に到達しています。
- つまり「脱獄していない実機上のアプリが待ち受けたポートへ、iproxy 転送で PC から届く」こと自体には実運用の前例があります。本プロジェクトの方式は、この実績のある経路に乗る設計です。
- ただし WDA は開発者向けの仕組み（テストバンドル等）で動く面もあり、「任意のサイドロード通常アプリでも同一に届く」とまではこの前例だけでは言えません。ここが §3 の不確実性につながります。

### 2.3 本プロジェクト側の設計上の手当て

BRIDGE-PROTOCOL §0 に既に織り込まれている点:

- iPhone アプリはポート **18765** で、全インターフェースに bind して待ち受けます。loopback 指定だと usbmux 経由で届かない事例があるためで、到達制御は bind 範囲ではなく暗号層（ペアリング + AEAD）で行います。
- Fedora 側は `127.0.0.1:18766` へだけ接続します。iproxy の待ち受けも localhost に限る運用を前提にします（THREAT-MODEL 参照）。

## 3. 不確実性と制約

未検証・要注意の項目です。推測で埋めず、実機で潰します。

### 3.1 iOS 17 以降の RemoteXPC 移行

- iOS 17 以降、開発者向けサービス（アプリのインストール、デバッグ、テスト実行など）は従来の usbmux / lockdown 系サービスから RemoteXPC（Remote Service Discovery）へ移行が進んでいます。
- Appium などの実務ツールは iOS 18 以降で RemoteXPC を優先しつつ、usbmux をフォールバックとして残しています。つまり usbmux 経路が即座に消えたわけではありませんが、「どの操作がどの経路で運ばれるか」は iOS バージョンで変わり得ます。
- 本プロジェクトが使うのは開発者向けサービスではなく「端末上の TCP 待ち受けポートへの接続中継」です。これがユーザーの iOS バージョンで通常アプリに対してどう扱われるかは、公開資料だけでは確定できません。
- **結論: 「通常アプリの待ち受けポートへの iproxy 転送がユーザーの iOS バージョンで届くか」は実機での確認が必須の未検証点です。** REAL-DEVICE-TEST の段階 (b) がその確認に当たります。

### 3.2 フォアグラウンド必須

- iOS アプリはバックグラウンドで suspend され、NWListener の待ち受けは維持されません（BRIDGE-PROTOCOL §5 にも明記）。
- したがって認証のたびに（正確には接続のたびに）アプリがフォアグラウンドで起動している必要があります。これは仕様上の制約として受け入れ、利用手順に明記します。「常駐して裏で受け付ける」ことは前提にしません。

### 3.3 その他の制約

- **ペアリングが前提**: 初回の `idevicepair pair` と iPhone 側の信頼確認なしには中継が始まりません。iOS のメジャーアップデート等でペアリング記録が無効化される場合があります。
- **ケーブルと USB の状態**: 充電専用ケーブル、ハブ経由の不安定さ、端末のロック状態などが疎通に影響します。切り分け手順（§5）に含めます。
- **ポート競合**: PC 側 18766、端末側 18765 が他プロセスに使われていると転送が成立しません。
- **アプリ未起動**: iproxy が転送先に接続できても、アプリが起動していなければ接続は拒否・切断されます。これは異常ではなく想定内です（段階表示で区別します）。
- **到達制御は暗号層**: §2.3 の通り全インターフェース bind のため、USB 以外（同一 LAN 等）からも TCP 的には到達し得ます。未ペアリングの相手はハンドシェイクで切断される設計ですが、実機で「ペアリングなしでは意味のある操作ができないこと」の確認は必要です。

## 4. この環境で実機確認ができていない理由（未実施の明示）

以下は言い訳ではなく、検証状態の記録です。

- **開発用 Muse VM（Ubuntu コンテナ）には USB デバイスがありません。** `/dev/uhid` も `usbmuxd` も `cargo` も初期状態では無く、iPhone を物理的に挿すことができません。この環境では実機 USB 疎通は検証不可能です。
- **ユーザーの Fedora 機へは Tailscale 経由ですが、合意により Funnel は普段 OFF で、作業セッション時だけ ON にする運用です。** したがって本レポート作成時点でも Fedora 実機でコマンドは実行できていません。
- よって本レポートで言えるのは「原理と前例」と「未検証点の洗い出し」までです。**実機での最終確認は未実施**であり、それを済ませるための手順書（REAL-DEVICE-TEST）と自動判定スクリプト（verify-usb-fedora.sh）を併せて用意しました。

実機セッションが開けたら、まず次を実行して結果を REAL-DEVICE-TEST の記録テンプレートに残してください:

```sh
scripts/verify-usb-fedora.sh
```

## 5. 失敗した場合の切り分け手順

疎通しないときは、上流（USB / ペアリング）から下流（アプリ）へ順に潰します。途中で飛ばさないこと。各段の担当コマンドと、REAL-DEVICE-TEST の段階対応も付けます。

### 段階 0: 物理・前提

- [] データ転送対応ケーブルか（充電専用ケーブルを疑う。純正または実績のあるケーブルに替えて再試行）
- [] ハブを外して直結で再試行したか
- [] iPhone がロック解除された状態か（ペアリング操作時は必須）
- 対応: REAL-DEVICE-TEST 段階 (a) の前提

### 段階 1: usbmuxd の起動（Fedora 側）

確認:

```sh
command -v usbmuxd idevice_id idevicepair iproxy ideviceinfo
systemctl status usbmuxd # または: pgrep -a usbmuxd
ls -l /var/run/usbmuxd # ソケットの有無
```

- ツールが無い → `sudo dnf install libimobiledevice usbmuxd libusbmuxd-tools`（REAL-DEVICE-TEST 参照）。
- usbmuxd が動いていない → サービス起動と有効化を確認する。USB 接続時に udev 経由で起動する構成もあるため、端末を挿した状態で再確認する。
- 対応: verify-usb-fedora.sh の段階 1–2

### 段階 2: 端末認識と trust（idevicepair）

確認:

```sh
idevice_id -l # UDID が出るか
ideviceinfo -k DeviceName # ペアリング済みなら情報が返る
idevicepair validate # ペアリング記録の妥当性
```

切り分け:

- `idevice_id -l` が空 → USB 認識そのものができていない。段階 0–1 に戻る。別ポート・別ケーブルでも同じかを見る。
- UDID は出るが `ideviceinfo` がエラー → 大抵は未ペアリングか、ペアリング記録の不整合。iPhone の画面に「このコンピュータを信頼しますか？」が出ていないか確認し、`idevicepair pair` を実行して端末側で信頼する。
- `idevicepair pair` が失敗する → 端末がロックされていないか、画面の確認ダイアログを見落としていないか、iOS を更新した直後で再ペアリングが必要になっていないかを確認する。
- **注意（スクリプトの範囲）**: verify-usb-fedora.sh は読み取り中心で、ペアリングの削除（`idevicepair unpair` 等の破壊的操作）はしません。再ペアリングが必要なら手順書を見ながら手動で行ってください。
- 対応: REAL-DEVICE-TEST 段階 (a)、verify-usb-fedora.sh の段階 3–4

### 段階 3: iproxy の起動とポート競合

確認:

```sh
iproxy 18766 18765
# 別ターミナルで:
ss -ltnp | grep 18766 # 待ち受けが立ったか
```

切り分け:

- `Address already in use` → 18766 が競合。`ss -ltnp` で占有プロセスを特定し、既存の iproxy ならそれを再利用するか、止めてよいものか確認してから扱う（無関係なプロセスを勝手に kill しない）。
- iproxy が端末に接続できない旨を出す → 段階 2 に戻る（ペアリング／端末認識の問題であることが多い）。
- UDID が複数ある環境では、対象端末を明示するオプションが必要な場合がある。
- 対応: REAL-DEVICE-TEST 段階 (b) の前半、verify-usb-fedora.sh の段階 5

### 段階 4: アプリ側の到達（iPhone 側）

確認の前提: iPhone アプリがフォアグラウンドで起動し、待ち受け表示が出ていること。

```sh
# Fedora 側から、iproxy 越しに 127.0.0.1:18766 への TCP 接続を試す
# (verify-usb-fedora.sh の段階 6 が hello ハンドシェイクの入口まで試します)
scripts/verify-usb-fedora.sh
```

切り分け:

- TCP 接続自体が拒否される → アプリ未起動、フォアグラウンドでない（suspend）、待ち受けポートの不一致（18765）を疑う。アプリを前面に出して直後に再試行する。
- TCP はつながるがハンドシェイクが進まない → アプリ側の待ち受け実装、bind の仕方、iOS バージョン起因の中継挙動（§3.1）を疑う。ここで初めて「iOS 17+ の不確実性」が現物の問題として確定します。その場合は iOS バージョンを記録し、§6 の報告に進んでください。
- ロック画面に戻った・アプリを切り替えた途端に切れる → フォアグラウンド必須（§3.2）の想定内の挙動。失敗としてではなく制約として記録する。
- 対応: REAL-DEVICE-TEST 段階 (b)

### 段階 5: iOS バージョンの記録

どの段で失敗しても、次を必ず記録します（REAL-DEVICE-TEST のテンプレート項目です）:

- iOS バージョンとビルド（設定 → 一般 → 情報）
- Fedora のバージョン、`usbmuxd` / `libimobiledevice` / `libusbmuxd-tools` のバージョン
- 失敗した段階、コマンド、出力そのもの（要約ではなく原文）

## 6. 失敗した場合の報告の仕方

実機で届かないことが確定したら、「できませんでした」で終わらせず、次を揃えて報告します（ユーザーの当初の指示: 失敗した場合は原因と制限を報告すること）。

1. 失敗した段階（§5 のどの段か）と、その段までの合格済み段階の一覧
2. iOS バージョン、Fedora 側ツールのバージョン、ケーブル・接続形態
3. 失敗時のコマンド出力原文（スクリプトの出力ごと）
4. 原因の切り分け結果: 「特定できた原因」か「iOS の中継挙動が原因と推定されるが断定できない」かを区別する
5. 代替案の有無と評価（例: RemoteXPC 経路の調査、到達方法の変更など。ただし未検証の代替案を「解決策」として提示しない）

## 7. 未検証項目の一覧（この文書分）

- [] Q3: ユーザー実機での `iproxy 18766 18765` → アプリ 18765 への到達
- [] iOS 17 以降（ユーザーの正確なバージョン）で通常アプリの待ち受けポートへの usbmux 中継が有効か
- [] 未ペアリングの接続がハンドシェイクで確実に切断され、意味操作に到達できないこと
- [] 長時間接続・複数回連続接続での中継の安定性（切断、再接続、iproxy の再起動）
- [] ハブ経由や省電力状態など、ユーザーの常用環境での再現性
