# THREAT-MODEL — 脅威モデル

対象: Phone-as-a-securitykey 全体（Fedora daemon、Bridge Protocol、電話アプリ）。
仕様の詳細は [BRIDGE-PROTOCOL.md](BRIDGE-PROTOCOL.md) を参照してください。この文書は「何を守り、誰から守り、どこまで守れて、どこから守れないか」を正直に書くためのものです。

未検証の対策を「効いている」とは書きません。対策の実装・検証状態も併記します。

---

## 1. 守るもの

| 資産 | 説明 | 置き場所 |
|---|---|---|
| 資格の秘密鍵（最重要） | WebAuthn 資格ごとの P-256 秘密鍵。漏れる・コピーされる・本人の確認なしに使われると、その資格でなりすまし放題になる | iPhone の Secure Enclave 内のみ |
| 本人確認の真正性 | 「署名した = 本人が rp を見て承認し Face ID を通した」が崩れると、鍵が漏れなくても悪用できる | iPhone アプリ + Secure Enclave の access control |
| 資格メタデータ | rp_id、user_id、user_name、credential_id、公開鍵、sign_count | iPhone の Keychain（秘密情報は含まない設計だが、利用サイトの推定材料にはなる） |
| ペアリング PSK | PC ⇄ 電話の通信の認証の土台。漏れると通信相手の偽装が可能になる | 電話: Keychain / Fedora: `~/.config/iphone-fido/pairing.bin` (mode 0600) |
| セッション鍵 | 接続ごとの通信の機密・完全性 | 両側のメモリ内のみ（永続化しない） |
| sign_count の単調性 | リプレイ／クローン検知の補助情報 | 電話の Keychain |

守らない・守れないと割り切るもの:

- Fedora 上のブラウザセッション自体（侵害された Fedora では、攻撃者は認証後のセッションをそのまま使える。本プロジェクトの範囲外）
- RP（GitHub / Google 等）側のアカウント回復手続きの強度
- iPhone の紛失・盗難そのもの（Face ID と Enclave が最後の砦。§5 参照）

## 2. 信頼境界

```text
信頼する: iPhone、Secure Enclave、iOS、ユーザーの目と指 (承認操作)
信頼しない: Fedora 上の他プロセス、USB 経路、LAN、ブラウザから渡るパラメータ全般
部分的に信頼: Fedora 上の自作 daemon とその実行環境
(侵害されると完全には守れない。§5 の残存リスク参照)
```

要点: Fedora 側は CTAP2 を終端し、ブラウザと電話の間に立つため、構造的に「騙しの余地」を持つ位置にいます。その余地を、電話側の独立した表示と承認で可能な限り潰すのが本設計の中心です。

## 3. 攻撃者像

| ID | 攻撃者 | 能力 | 狙い |
|---|---|---|---|
| A1 | Fedora 上の悪性プロセス（ユーザー権限） | localhost への接続、ファイル読み取り（権限の範囲内）、daemon への成りすまし試行、iproxy の待ち受けへの接続 | PSK の窃取、電話への直接の署名要求、セッションの盗聴・改ざん |
| A2 | Fedora 上の他プロセス（ペアリング未実施の第三者プロセス含む） | `127.0.0.1:18766` への接続試行 | ハンドシェイク突破、なりすまし接続 |
| A3 | USB 経路上の盗聴・改ざん者 | 悪性ハブ／ケーブル、USB パケットの傍受・注入 | 通信内容の読み取り、署名要求の改ざん、リプレイ |
| A4 | 中間者（経路の差し替え） | iproxy の差し替え、偽の転送先、電話アプリへの成りすまし（PC 側から見た偽電話） | PC に偽の応答を返させる、電話に偽の要求を送る |
| A5 | RP を偽装する要求元 | 悪性サイト／侵害された経路経由で、別の rpId の認証を正規の文脈に見せかける | ユーザーが意図しない RP への認証・登録 |
| A6 | 物理アクセス者 | 盗んだ／置き忘れた iPhone、接続されたままの PC の操作 | Face ID なしでの署名、承認の代行 |
| A7 | 侵害された Fedora 上の daemon 自体（最悪ケース） | 正規の PSK を持ち、正規の経路で電話に要求を送れる | 表示と実要求を食い違わせた承認騙し（§5 で限界を明記） |

対象外とする攻撃者: iOS / Secure Enclave の実装を破る能力を持つ者、ユーザーを脅迫・強制できる者。これらは本プロジェクトでは防御を約束しません。

## 4. 対策

各対策に、対応する攻撃者と状態（仕様確定／実装中／未検証）を付けます。

### 4.1 鍵は Enclave 内のみ（A1, A3, A6）

- 秘密鍵は Secure Enclave で生成し、Enclave 外に出しません。Fedora が受け取るのは公開鍵、authData、署名だけです（BRIDGE-PROTOCOL §3.2, §3.3）。
- Fedora が侵害されても、秘密鍵の抽出はできません。攻撃ができるのは「電話に署名を頼む」ところまでで、§4.2 のゲートが残ります。
- アルゴリズムは Secure Enclave の制約通り P-256、WebAuthn の ES256 (COSE `-7`) と一致します。
- 状態: 仕様確定。実機での鍵生成・保持の動作は。

### 4.2 電話側で authData を組み立て、rp を表示する（A5, A7 への部分対策）

- PC は任意バイト列への署名を電話に求めません（BRIDGE-PROTOCOL §3 の原則）。電話が `rp_id` から `SHA-256(rp_id)` を含む authData を自ら組み立てます。
- つまり「表示した rp」と「署名対象に含まれる rpIdHash」は同じ電話側処理から出ます。PC が署名対象だけを差し替えることはできません。
- ただし PC が要求自体に嘘の `rp_id` を入れる余地は残ります。その場合でも電話の画面にはその嘘の rp がそのまま表示されるため、ユーザーが気付ける余地は残ります（§5 の限界も参照）。
- 状態: 仕様確定。表示文言・見落としにくさの実機確認は。

### 4.3 タップ承認 + Face ID の二重ゲート（A1, A6, A7 への部分対策）

- USB がつながっているだけでは何も承認されません。
- `create_credential` / `get_assertion` は、電話の画面で rp_id と user_name を見てユーザーが「作成」「承認」をタップすることが必須です。タップがなければ署名しません（拒否は `user_cancelled`）。
- 署名そのものは Secure Enclave の access control（`.privateKeyUsage` + `.biometryCurrentSet`、BRIDGE-PROTOCOL §3.2）により Face ID をハードウェアレベルで必須にします。アプリの UI ロジックだけに依存しない点が重要です。`.biometryCurrentSet` のため、生体情報を再登録すると既存鍵は使えなくなります（これは仕様上の安全側の挙動です）。
- 操作ごとに認証コンテキストを新規にし、過去の認証の使い回しをしません。
- 状態: 仕様確定。Face ID prompt が出る正確なタイミング（鍵生成時ではなく署名時であること含む）は（BRIDGE-PROTOCOL §5）。

### 4.4 PSK ペアリング + SAS 確認（A2, A4）

- 初回のみ、電話が生成した 32 byte の PSK を Base32（52 文字）で画面表示し、ユーザーが Fedora 側 CLI に手入力します。PSK を USB 経路上に流さない帯域外共有です（BRIDGE-PROTOCOL §1）。
- SAS: 両側で `SHA-256(PSK || "iphone-fido-sas-v1")` から導いた 6 桁を表示し、ユーザーが一致を目視確認します。入力ミスや、別の相手とペアリングしてしまった事故をここで検出します。
- Fedora 側の PSK は mode 0600 のファイルに保存します。ユーザー権限を奪われた攻撃者（A1）からは守れません（§5）。
- 状態: 仕様確定。相互実装での一致確認は。

### 4.5 一時 ECDH + AEAD によるセッション保護（A2, A3, A4）

- 接続ごとに一時 P-256 鍵で ECDH し、`ikm = ecdh || PSK`、HKDF (SHA-256) で方向別鍵と confirm 鍵を導出します（BRIDGE-PROTOCOL §2）。PSK を知らない相手とは鍵が一致せず、confirm の HMAC 検証で切断します。
- 以後の全フレームは ChaCha20-Poly1305（seq を nonce に使う単調増加方式）で暗号化・認証します。復号失敗は即切断です。
- これにより USB 経路の盗聴（A3）では中身が読めず、改ざんは検出され、偽電話／偽 PC（A4）は confirm を通れません。
- 前方秘匿性は一時的 ECDH により部分的です: セッション鍵は ECDH に依存しますが、PSK が後から漏れると過去の記録の復号可能性の評価が変わるため、「完全な前方秘匿」とは主張しません（§5）。
- 状態: 仕様確定。相互実装の相互運用と、復号失敗時の切断挙動は。

### 4.6 その他の対策

- **フレーム長上限 1 MiB**: 異常に大きい入力でのメモリ枯渇を抑えます（BRIDGE-PROTOCOL §0）。
- **sign_count の単調増加**: 電話側で +1 して永続化し、authData に含めて返します。Fedora 側は加工しません（§4.1 の橋渡し役に徹する）。限界は §5。
- **モック電話の分離**: 開発用モックは `--mock-phone` 明示時のみ有効で起動時に警告を出します（BRIDGE-PROTOCOL §4）。モック資格を本物と誤認させない運用が前提です。
- **localhost 限定の待ち受け（Fedora 側）**: iproxy の転送先接続は `127.0.0.1:18766` のみ。daemon は外部公開しません。ただし iPhone 側は全インターフェース bind のため、電話側の到達制御は暗号層が担います（FEASIBILITY §3.3）。
- **attestation は `fmt:"none"`**: 証明書チェーンを持たない代わりに、attestation による追跡可能性を避けます。帰結は §5。

## 5. 残存リスク（正直な限界）

ここに書いたものは「対策済み」とは言いません。利用判断の材料にしてください。

### 5.1 Fedora 侵害時の承認騙しは完全には防げない（A7）

- daemon が侵害されると、攻撃者は正規の PSK と正規の経路を持ちます。暗号層は素通りです。
- 最後の砦は電話の画面表示とユーザーの確認ですが、攻撃者は「ユーザーが本当に認証したいタイミング」に紛れて悪性の要求を送ることができます。ユーザーが rp 表示を見落とせば、そのまま署名されます。
- 緩和: 電話側表示（§4.2）、二重ゲート（§4.3）、操作のたびの Face ID。これらは確率を下げますが、ゼロにはしません。
- **結論: Fedora が完全に侵害された状態で、ハードウェアキーと同等の保証は主張しません。** 一般的な商用セキュリティキーでも「侵害された PC 上のセッション」は守れませんが、本設計はそれに加えて「要求の発生源が PC 側プログラムである」分、表示の独立性に限界があります。

### 5.2 `none` attestation の帰結

- `fmt:"none"` のため、RP は「この資格が本物の Phone-as-a-securitykey で作られた」ことを暗号学的に検証できません。ソフトウェア実装で作った資格と区別が付きません。
- 帰結 1: 高い保証レベルを求める RP（企業ポリシー等で attestation を必須にする先）では登録を拒否される可能性があります。
- 帰結 2: GitHub / Google が実際に受理するかはです（REAL-DEVICE-TEST の段階 (f), (g) で確認）。受理されなかった場合、その事実を報告し、attestation 方式の再検討が別途必要になります。
- 帰結 3: 逆に利点として、デバイス個体に紐づく証明書による追跡はされません。

### 5.3 sign_count の扱い

- 本実装は電話側で sign_count を単調増加させますが、RP 側が clone 検知に sign_count をどう使うかは RP の実装依存です。差分が出ても警告で終わる RP もあれば、拒否する RP もあります。
- 電話の Keychain データが失われる／別端末に移る等でカウンタが巻き戻ると、RP によってはクローンと誤検知される可能性があります。バックアップと復元の設計は本バージョンの範囲外です。
- また sign_count は「鍵のコピーが存在しないこと」の証明にはなりません（Enclave の性質に依存する主張であり、attestation が無い以上 RP からは検証不能です。§5.2 と同根です）。

### 5.4 その他の残存リスク

- **PSK の保管（Fedora 側）**: mode 0600 は他ユーザーからの保護です。同一ユーザー権限の悪性プロセス（A1）が読めれば、電話への成りすまし接続が可能になります。ただし署名には依然として電話側の承認 + Face ID が要るため、PSK 単独では認証は完結しません。
- **前方秘匿性の限定**: §4.5 の通り。USB 経路を長期に記録され、将来 PSK が漏れた場合の評価は残ります。
- **可用性への攻撃**: USB 抜去、iproxy の終了、アプリの suspend 等で認証不能にできます。可用性は本モデルの防御対象外です（fail-closed であり、勝手に通ることはありません）。
- **UI の見落とし**: rp 表示が小さく／紛らわしい場合、ユーザーが誤承認する可能性は残ります。表示設計の実機評価はです。
- **資格メタデータの露出**: 電話を手にした者や Keychain にアクセスできる者は、どの RP に資格があるかを知り得ます。秘密鍵そのものは含まれません。
- **サイドロード配布の真正性**: インストールするアプリ自体が正規ビルドであることの保証は、配布経路（署名、入手元）に依存します。改ざんされたアプリはこのモデル全体を無効化します。入手元と署名の確認を利用手順に含める必要があります。
- **iOS / RemoteXPC の仕様変更**: 将来の iOS で中継経路が変わると、可用性だけでなく「どの経路を通るか」の前提も変わります。FEASIBILITY §3.1 参照。

## 6. セキュリティ上の約束（不変条件）

実装が変わっても、次を破る変更はしません。破る必要が出たら、この文書と BRIDGE-PROTOCOL を先に改訂し、ユーザーに明示します。

1. 秘密鍵を Fedora に渡さない。出るのは公開鍵、authData、署名だけ。
2. USB 接続だけで認証を承認しない。タップ承認 + Face ID を必須にする。
3. PC は任意バイト列への署名を求めない。authData は電話が組み立てる。
4. 未ペアリングの相手と意味のある操作をしない。ハンドシェイク失敗は切断する。
5. モック電話の資格を本物として扱わない・扱わせない。
